# План реализации: движок программы и операционный центр трекера

> Статус на 14.09.2026: программная часть MVP реализована. Пилот на реальном потоке, замеры работы трекеров и внешние email/Telegram-каналы намеренно остаются отдельным следующим этапом.

## Цель

Превратить кабинет акселератора из набора разрозненных разделов в единый рабочий контур:

```text
правила программы → фактический прогресс → сигналы риска → очередь действий → результат
```

Система должна отвечать на два вопроса:

1. Что участник действительно выполнил?
2. Что организатору или трекеру нужно сделать сейчас?

## Принципы

- Один источник истины для прогресса программы.
- Любой процент и любой риск должны быть объяснимыми.
- Обязательные и необязательные элементы не смешиваются.
- AI предлагает вывод или действие, но не меняет прогресс без правила или подтверждения.
- Автоматические действия должны быть обратимыми и попадать в журнал.
- Сначала поддерживается линейная программа; сложный граф зависимостей откладывается.

## Целевой результат MVP

Участник видит актуальный статус этапов без обязательного ручного клика после выполнения всех требований. Трекер открывает раздел «Сегодня» и получает приоритизированную очередь конкретных действий.

### Вне MVP

- полноценный визуальный конструктор workflow;
- произвольный граф зависимостей между этапами;
- автоматическая отправка сообщений во все внешние каналы;
- AI-оценка риска как единственный источник статуса;
- сложные формулы взвешенного прогресса.

## 1. Движок программы

### 1.1. Правила завершения этапа

Для этапа определить `completion_policy`:

```json
{
  "mode": "auto",
  "materials": "all_required",
  "homework": "all_required",
  "pitchy_actions": "all_required",
  "attendance": "none",
  "manual_confirmation": false
}
```

Поддержать режимы:

- `auto` — этап завершается, когда выполнены обязательные элементы;
- `manual` — после выполнения требований нужно подтверждение трекера;
- `none` — этап информационный и не влияет на обязательный прогресс.

Правила по умолчанию:

- обязательные опубликованные этапы входят в знаменатель прогресса;
- необязательные этапы не уменьшают процент;
- этап без обязательных элементов считается завершённым автоматически;
- незачтённая или просроченная домашка блокирует этап;
- посещение блокирует этап только при явно включённом правиле;
- обязательное действие Pitchy должно иметь статус `ready`;
- исключение (`waived`) всегда требует причины и автора.

### 1.2. Состояния этапа

В API и интерфейсе использовать единый набор:

- `locked` — закрыт предыдущим этапом или датой открытия;
- `available` — доступен для прохождения;
- `in_progress` — начат, но требования не выполнены;
- `completed` — требования выполнены;
- `overdue` — истёк срок;
- `waived` — требование снято вручную.

Для завершения хранить источник:

- `auto`;
- `manual`;
- `waived`.

### 1.3. Изменения в данных

Использовать существующие сущности `AcceleratorProgramStage`, материалы, домашние задания, события и Pitchy-артефакты. Добавить:

- `completion_policy` у этапа;
- `due_at` у этапа, если срок не задаётся только домашкой;
- `completion_source` и `waiver_reason` в `AcceleratorProgramStageProgress`;
- при необходимости `last_evaluated_at` для диагностирования расчёта.

Не дублировать в базе вычисляемый процент: хранить факты выполнения, а процент рассчитывать сервисом.

### 1.4. Сервис прогресса

Создать `ProgramProgressService` с методами:

- `get_stage_state(membership_id, stage_id)`;
- `get_membership_progress(membership_id)`;
- `get_cohort_progress(cohort_id)`;
- `explain_stage_state(membership_id, stage_id)`;
- `complete_or_reconcile_stage(...)`.

Ответ API для этапа должен содержать:

```json
{
  "state": "blocked",
  "completed": 0,
  "required_total": 3,
  "completed_required": 2,
  "blockers": [
    {
      "kind": "homework",
      "id": 41,
      "title": "Проверить сегмент",
      "reason": "Ожидается проверка трекера"
    }
  ]
}
```

### 1.5. Интерфейс программы

Для организатора:

- список этапов с прогрессом `2/3`;
- видимый список блокеров;
- настройка обязательности и режима завершения;
- действие «снять требование» с обязательной причиной;
- журнал ручных изменений.

Для участника:

- понятные состояния этапов;
- список обязательных элементов;
- статус «что осталось сделать»;
- отсутствие ложного `50%`, если все фактические требования выполнены.

## 2. Операционный центр трекера

### 2.1. Сигналы

Создать детерминированный `TrackingSignalsService`. На первом этапе поддержать:

- `homework_overdue` — просрочена домашка;
- `homework_needs_revision` — работа возвращена на доработку;
- `stage_blocked` — следующий этап заблокирован;
- `no_checkin` — нет чек-ина за заданный период;
- `low_attendance` — низкая посещаемость при включённом правиле;
- `no_activity` — нет активности заданное количество дней;
- `required_action_open` — обязательное действие не завершено;
- `audit_recommendation_open` — рекомендация аудита не превращена в действие.

Каждый сигнал должен иметь:

- `membership_id`;
- `kind` и стабильный `fingerprint` для дедупликации;
- `severity`: `low`, `medium`, `high`;
- `title`, `reason`, `due_at`;
- `source_type`, `source_id`;
- `action_url` или тип быстрого действия;
- `state`: `open`, `acknowledged`, `snoozed`, `resolved`.

### 2.2. Очередь работы

На первом этапе очередь можно рассчитывать на лету из фактов программы и трекинга. Сохранять только пользовательские изменения состояния, отложенные сигналы и ручные задачи.

Порядок по умолчанию:

1. высокий риск;
2. просроченные элементы;
3. ближайший дедлайн;
4. отсутствие активности;
5. низкий риск.

Карточка очереди:

```text
Егор · высокий приоритет
Этап «Проверка спроса» заблокирован
Домашка возвращена на доработку трекером

[Открыть работу] [Назначить задачу] [Отложить]
```

### 2.3. Быстрые действия

Из очереди должны быть доступны:

- открыть карточку участника;
- открыть конкретную домашку или этап;
- назначить задачу;
- отправить напоминание;
- отметить сигнал принятым в работу;
- отложить до даты;
- закрыть после проверки.

Закрытие сигнала не должно автоматически менять исходный факт: закрытая задача не делает домашку зачтённой.

### 2.4. Представления интерфейса

В операционном центре нужны вкладки или фильтры:

- «Сегодня»;
- «Высокий риск»;
- «Просрочено»;
- «Без активности»;
- «Все участники».

Фильтры:

- трекер;
- этап;
- тип сигнала;
- приоритет;
- срок;
- статус.

Верхняя строка метрик:

- открытые сигналы;
- высокий риск;
- просроченные домашки;
- участники без чек-ина;
- задачи на сегодня.

## 3. Связь двух подсистем

Движок программы остаётся источником фактов и статусов. Операционный центр только читает эти статусы и создаёт действия.

```text
материал / домашка / событие / артефакт
             ↓
      ProgramProgressService
             ↓
      TrackingSignalsService
             ↓
       Work Queue трекера
             ↓
   задача / напоминание / проверка
```

После любого изменения факта пересчитывать затронутые этап и сигналы:

- принятие домашки;
- возврат на доработку;
- завершение материала;
- завершение Pitchy-действия;
- чек-ин;
- посещение;
- изменение дедлайна;
- ручное исключение.

## 5. Исправление CSV-экспорта

### Проблема

Экспорт заявок формируется в браузере через запятую и открывается в русской локали Excel одной колонкой. На экране это выглядит как строка с разделителями внутри ячейки, а не как таблица.

### Требования к формату

- Использовать `;` как разделитель по умолчанию для русской локали.
- Сохранять UTF-8 с BOM, чтобы кириллица корректно открывалась в Excel.
- Экранировать только значения, содержащие разделитель, кавычки или перенос строки; внутренние кавычки удваивать.
- Использовать `CRLF` между строками для совместимости с Excel.
- Не допускать формульной инъекции: значения, начинающиеся с `=`, `+`, `-` или `@`, должны экспортироваться как текст.
- Даты передавать в едином читаемом формате с часовым поясом, без случайного смешения локального времени и UTC.
- Заголовки и порядок колонок должны быть стабильными и совпадать с названиями в интерфейсе.
- Применить единый сериализатор ко всем CSV акселератора: заявки, отчёт участников, посещаемость и Demo Day.

### Реализация

- [x] Вынести сериализацию в общую функцию/утилиту CSV.
- [x] Перевести клиентский экспорт заявок из `ApplicationManager` на общий сериализатор.
- [x] Проверить серверные экспорты и привести разделитель, BOM, переносы строк, MIME-тип и `Content-Disposition` к единому формату.
- [x] Сохранить фильтры текущего экрана: экспортируются только отображаемые строки.
- [x] Добавить понятное имя файла с типом экспорта и датой формирования.

### Состав таблиц

Не делать одну универсальную выгрузку со всеми данными. Каждый экспорт должен отвечать на отдельный рабочий вопрос организатора.

#### Экспорт «Заявки»

Основной рабочий список:

- ID заявки;
- имя участника;
- email;
- тип заявки: «Проект» или «Участник без проекта»;
- название проекта;
- статус заявки: «На рассмотрении», «Одобрена», «Отклонена»;
- статус участия: «Не зачислен», «Зачислен», «Завершил»;
- дата подачи;
- дата решения;
- назначенный трекер;
- следующее действие;
- ссылка на карточку заявки.

Разделить «статус заявки» и «статус участия», чтобы не смешивать решение по заявке с фактом зачисления.

#### Экспорт «Полные анкеты»

- базовые данные участника идут первыми;
- вопросы отображаются в порядке формы;
- в заголовках используются человекочитаемые названия, а не ключи API;
- массивы и множественный выбор объединяются через ` | `;
- длинные ответы сохраняются полностью;
- пустые ответы остаются пустыми;
- полный экспорт запускается отдельно и не перегружает рабочий список заявок.

#### Экспорт «Участники и прогресс»

- имя и email;
- статус участника;
- трекер;
- программа: `завершено из общего` и процент;
- домашние задания: зачтено, на проверке, просрочено;
- посещение;
- последний чек-ин;
- последняя активность;
- уровень риска и причина риска;
- открытые задачи.

Квоты и прочие технические поля не включать в основной рабочий экспорт без отдельного режима.

#### Отдельные специализированные экспорты

- «Посещаемость» — участник, email, статус, время отметки, комментарий;
- «Результаты Demo Day» — место, проект, участник, оценки, результат, ссылки на презентацию и видео.

### Представление значений и порядок строк

- Не экспортировать сырые статусы `approved`, `enrolled`, `needs_revision` и подобные — использовать русские подписи.
- Даты отображать единообразно: `ДД.ММ.ГГГГ ЧЧ:ММ` с явно выбранным часовым поясом.
- В заявках сортировать сначала записи, требующие решения, затем уточнения, одобренные, отклонённые; внутри группы — новые сверху.
- В списке участников сначала показывать высокий риск, затем просроченные задачи и отсутствие чек-ина.
- Экспорт сохраняет текущие фильтры экрана, но названия и порядок колонок остаются стабильными.
- Технический ID оставлять первым и использовать только для связи с системой, не делать его главным отображаемым полем.

- [x] Пустые значения не ломают структуру строки.

## 7. Критерии готовности MVP

- Процент программы одинаков в кабинете участника, отчёте и tracking dashboard.
- Для каждого неполного этапа можно увидеть точную причину.
- Трекер открывает рабочий день из одной очереди.
- Любой элемент очереди ведёт к конкретному действию.
- Повторные загрузки и обновления не создают дубли.
- Все ручные исключения и решения видны в аудите.
- На реальном потоке организатор понимает состояние участников без ручной сверки нескольких разделов.

## 9. Общая админ-панель: таблица пользователей

### Проблема

Таблица пользователей в общей административной панели не помещается в доступную ширину: правые колонки и действия уходят за пределы экрана, поэтому на десктопе приходится прокручивать таблицу по горизонтали.

### Требования к layout

- Увеличить максимальную ширину контейнера общей админ-панели для экранов десктопа.

## 10. Контекстные формулировки для организатора и резидента

### Проблема

Один и тот же факт трекинга сейчас отображается одинаково для разных аудиторий. Формулировка «Резидент отметил сложности» понятна организатору, но в кабинете самого резидента звучит как сообщение о другом человеке. Текст должен зависеть от того, кто смотрит карточку, а не дублироваться в каждом компоненте вручную.

### Принцип

Разделить:

1. **Факт** — что произошло в системе: резидент отправил чек-ин и выбрал уровень состояния `yellow` или `red`.
2. **Код причины** — стабильный машинный идентификатор, например `checkin_health_yellow`.
3. **Аудиторию** — `resident`, `tracker`, `organizer` или `admin`.
4. **Текст** — локализованное представление причины для выбранной аудитории.

Организатор, трекер и администратор считаются внутренней аудиторией и получают третье лицо. Резидент получает обращение на «вы». Это правило должно применяться во всех местах, где показывается риск или состояние поддержки: «Сегодня», трекинг, карточка участника, рабочая очередь, уведомления и экспорт.

### Матрица формулировок MVP

| Код причины | Внутренняя аудитория | Резидент |
|---|---|---|
| `checkin_health_yellow` | Резидент отметил сложности | Вы отметили сложности |
| `checkin_health_red` | Резидент отметил критические сложности | Вы отметили критические сложности |
| `checkin_missing` | Резидент ещё не заполнил чек-ин | Вы ещё не заполнили чек-ин |
| `homework_overdue` | Просрочена домашка | У вас просрочена домашка |
| `homework_needs_revision` | Домашка возвращена на доработку | Домашку нужно доработать |
| `tracker_not_assigned` | Трекер ещё не назначен | Трекер ещё не назначен; организатор уже видит это |

Факты, не связанные с действием резидента, не нужно искусственно переводить в первое лицо. Например, дату встречи, отсутствие назначенного трекера или системную ошибку лучше показывать нейтрально. Для критических состояний сохранять одинаковую степень срочности в обеих аудиториях.

### Контракт данных

API риска должно возвращать структурированные причины, например:

```json
{
  "code": "checkin_health_yellow",
  "severity": "medium",
  "actor": "resident",
  "text": "Резидент отметил сложности",
  "available_texts": {
    "resident": "Вы отметили сложности",
    "staff": "Резидент отметил сложности"
  }
}
```

Рекомендуемый вариант для переходного периода:

- сохранить текущий массив `reasons` для старых клиентов;
- добавить `reason_items` с `code`, `severity`, `actor` и текстом для текущей аудитории;
- сервер выбирает аудиторию по правам текущего пользователя, а не принимает произвольное значение из браузера;
- вынести словарь формулировок в одну функцию/слой локализации;
- не зашивать фразы в `ResidentToday`, `ParticipantDrawer` и другие компоненты.

Если один риск состоит из нескольких причин, сортировать их по severity и показывать первой наиболее важную. В раскрытом состоянии можно показать остальные причины; каждая из них должна быть отрендерена по той же матрице.

### Правила поведения интерфейса

- В кабинете резидента не использовать третье лицо («Резидент отметил…»).
- В интерфейсе организатора и трекера не обращаться к резиденту на «вы».
- Заголовок и пояснение карточки должны использовать одну аудиторию; нельзя смешивать «Вы отметили сложности» с «Организатор уже видит это» без явной роли.
- Для resident-версии добавлять следующий шаг: открыть чек-ин, связаться с трекером или посмотреть рекомендации.
- Для staff-версии добавлять операционное действие: открыть карточку, написать резиденту, назначить задачу или открыть очередь.
- При смене роли/режима просмотра текст должен обновляться без изменения самого факта риска.
- Не менять историю чек-инов и значения риска ради новой формулировки: меняется только представление.

- [x] Добавить единый resolver текста по паре `reason_code + audience`.

## 11. Команда участника без проекта

### Сценарий

Участник может прийти в акселератор без готового проекта, сформировать идею в процессе обучения и собрать команду из других участников без проектов. Это нормальный путь акселератора, а не ошибка или неполное резидентство:

1. участник подаёт заявку без проекта;
2. организатор одобряет заявку, участник подтверждает участие и получает статус `enrolled`;
3. участник создаёт команду со статусом «Проект формируется»;
4. приглашает или принимает других зачисленных участников;
5. создаёт проект или выбирает собственный существующий проект;
6. привязывает проект к команде;
7. после привязки становятся доступны проектные функции: аудит, проектные задания, демо-день и другие функции, требующие проекта.

Текущая проверка «создать команду можно только при наличии проекта» блокирует этот сценарий. При этом `project_id` команды уже допускает `NULL`, поэтому ограничение находится в бизнес-логике создания, а не является обязательным ограничением модели данных.

### Целевая модель

Разделить три независимых объекта:

- **Резидентство** — право участника работать в потоке;
- **Команда** — объединение участников, которое может существовать до появления проекта;
- **Проект** — продуктовая сущность, которую команда привязывает позже.

Для команды использовать два понятных состояния:

- `project_pending` — команда формируется, проект ещё не привязан;
- `active` — к команде привязан проект и доступны проектные функции.

Если добавление нового статуса создаёт лишнюю миграцию, на первом этапе можно оставить `status=active` и использовать вычисляемый признак `project_attached`, но в API и UI всё равно явно показывать «Проект формируется».

Правила владения:

- создать команду может любой зачисленный резидент, даже если у него нет проекта;
- владелец команды — создатель команды и его активное резидентство;
- привязать проект может владелец или организатор;
- проект должен принадлежать владельцу либо быть явно передан ему организатором;
- один проект может быть привязан только к одной активной команде в рамках потока;
- участники команды не обязаны иметь собственные проекты;
- смена капитана переносит право управления командой, но не меняет историю проекта.

### Доступ к функциям

| Состояние | Команды | Проектные функции |
|---|---|---|
| `accepted` | просмотр приветствия и правил, без изменения состава | недоступны |
| `enrolled`, без проекта | создать/вступить/пригласить в команду | недоступны до привязки проекта |
| `enrolled`, проект команды привязан | полный доступ по роли | доступны участникам команды по правилам модуля |
| `suspended` | просмотр, без новых приглашений и заявок | недоступны |
| `completed` | итоговый просмотр | новые изменения недоступны |

Статус `accepted` не считать полноценным зачислением: это решение организатора, которое ещё требует подтверждения участника. В интерфейсе явно разделить «Заявка одобрена» и «Участие подтверждено».

### Навигация

Для резидента порядок верхнего уровня:

`Сегодня` · `Мой путь` · `Мой профиль` · `Команда` · `Поддержка` · `Результаты`.

Раздел команды больше не должен находиться внутри «Поддержки». Внутри него разместить:

- моя команда;
- найти команду;
- приглашения и заявки;
- эксперты, если соответствующий модуль включён.

Для организатора создать отдельный раздел `Команды и трекеры`, объединив управление командами, подбор участников и назначение трекеров. В «Поддержке» оставить трекинг, чек-ины, задачи и обратную связь.

Сохранить поддержку старого deep link `section=matching`, чтобы старые закладки продолжали открывать новый раздел.

### Интерфейс команды без проекта

Вместо блокирующего сообщения показывать форму создания команды:

> Создайте команду и соберите участников. Проект можно добавить позже.

Карточка такой команды должна показывать:

- название команды;
- количество участников и свободные места;
- владельца и назначенного трекера;
- статус «Проект формируется»;
- кнопку «Добавить проект»;
- понятное ограничение: аудит и проектные функции появятся после привязки проекта.

После создания проекта показывать следующий шаг «Привязать проект к команде», а не требовать повторно создавать команду.
