# Ускорение МТУСИ.Бизнес, 367 участников

База изменений: production-релиз 2e52a72 с отдельно выложенным исправлением админки. Изменения перенесены в чистую копию актуального кода, с сохранением входа по логину, зачёта исторических версий домашних работ и индивидуальных сроков.

## Подтверждённая задержка

Рабочий cohort_id=5: 367 участников, 14 этапов, 4 задания. Caddy зафиксировал два ответа tracking-dashboard по 141–147 с (медиана 144,222 с), один report — 86,150 с. Analytics и operations-health отвечали в пределах примерно половины секунды.

## Изменения

- Обзор получает компактный overview-summary вместо полного отчёта и сигналов по каждому участнику. Заявки и списки участников загружаются при открытии нужного раздела. Карточки обновляются независимо.
- ProgramProgressService получает данные этапов и требований сразу для разрешённого набора участников. Один и тот же алгоритм расчёта используется в обычном и пакетном режимах. Снимок ограничен одним вызовом; операции записи с ним запрещены.
- Чтение прогресса больше не меняет last_evaluated_at тысяч записей. Пересчёт с сохранением продолжает обновлять его.
- В полном отчёте прогресс, риски, индивидуальные сроки, квоты и открытые задачи загружаются пакетно. Квоты читаются двумя SQL с сохранением приоритета индивидуальных лимитов, месячного периода, даты начала и безлимитных значений; списание квот не менялось.
- Трекинг повторно использует уже рассчитанный прогресс. Сигналы, последние аудиты, задачи и пользовательские состояния сигналов загружаются общими выборками.
- participant_results остаётся источником зачтённых версий работ: переход команды не переносит заслуги старых участников новым. Учитываются выбранная аудитория и индивидуальные исключения по срокам.
- Список участников получает личных и командных трекеров двумя общими запросами.
- Форма массового назначения задач запрашивает обычный список участников, а не запускает повторный полный tracking-dashboard.
- Второстепенные разделы обоих кабинетов загружаются по требованию. Повторные запросы при немедленном перенаправлении участника устранены однократной передачей данных в памяти с ограничением 30 секунд и очисткой при смене авторизации.
- Все runtime overrides проверяются одной выборкой с сохранением приоритета областей действия и срока действия.

## Проверки

- 117 серверных тестов прошли; 3 проверки требуют PostgreSQL row locks и пропущены в локальном SQLite-прогоне. Штатная CI-проверка PostgreSQL обязательна перед выкладкой.
- 31 браузерный сценарий Chromium прошёл, включая явные ошибки админки, независимый показ карточек обзора, загрузку списков по требованию и передачу данных входа.
- Production-сборка Next.js и TypeScript завершены успешно.
- Тест с 10 и 367 участниками, 14 содержательными этапами, четырьмя заданиями, зачтённой версией, выбранной аудиторией, индивидуальным сроком, waived/manual/none и будущей разблокировкой: прогресс — 12 SQL, сигналы — 5 SQL, полный tracking-dashboard — 50 SQL при обоих размерах. На локальном SQLite 367 участников обработаны за 0,288 с. Это не браузерный production-замер.
- Проверка на данных рабочего потока выполнялась в отдельном Python-процессе с временной копией изменённых модулей и транзакцией PostgreSQL REPEATABLE READ, READ ONLY. Исходники работающего приложения и данные базы при проверке не менялись. Все использованные ORM-объекты оставались неизменёнными.

Полный ответ содержал 367 участников и 1097 сигналов. Для первого, среднего и последнего участника значения прогресса и рисков совпали с прежним одиночным расчётом. Значения риска сравнивались после одинакового преобразования datetime в JSON.

Миграции базы не нужны. Общий кеш между пользователями не добавлен: доступ и актуальные данные проверяются при каждом запросе. Скорость загрузки в конкретном браузере зависит также от сети, первоначальной загрузки JS и объёма полного отчёта.
