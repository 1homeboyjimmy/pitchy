# План переработки кабинета участника: проект, поддержка, результаты

> Состояние проекта на 18.09.2026. План уточняет разделы 13.2, 15.4–15.7, 16.2 и 18 приложенного `accelerator-platform-refactoring-guide.md`. Описания в приложенном руководстве и скриншотах используются как проектные материалы; источником фактического поведения служит текущий код и API.

## Цель

Довести разделы «Мой проект», «Команда и поддержка» и «Результаты» до логики нового кабинета участника: понятный следующий шаг, прямой переход к действию, честные пустые состояния и единый тёмный стиль Pitchy. Сохранить действующие права, командные операции, историю и ограничения модулей.

## Принципы данных и прав

1. Разделять **заполненность паспорта** (`readiness_index`), **оценку аудита проекта** и **оценку Demo Day** (`final_score`). Они получаются из разных источников и не подменяют друг друга.
2. Не расширять доступ интерфейсом. Сервер подтверждает право на чтение, изменение и публикацию; скрытая кнопка не считается проверкой права.
3. Показывать только включённые для потока модули. Если разделу нечего показать, использовать объяснимое пустое состояние, а не ложный процент или неработающее действие.
4. Переиспользовать рабочие сценарии команды, трекинга, аудита, рекомендаций и артефактов. Перенос не должен сбрасывать историю, видимость материалов или права капитана.
5. Сохранять `membership_id`, `cohort_id`, `project_id`, выбранный раздел и адресуемый объект в допустимом URL; сервер повторно проверяет доступ при открытии прямой ссылки.

## 1. Мой проект / Мой профиль

### Целевой экран

- Для участника с проектом: название и короткое описание, явная «Заполненность паспорта — N%», следующий незаполненный обязательный блок, кнопка «Редактировать паспорт» при разрешённой записи или «Посмотреть паспорт» при разрешённом чтении.
- Компактная сводка аудита со ссылкой «Открыть аудит» только при включённом модуле; оценку аудита подписывать отдельно.
- Команда и рекомендации в контексте проекта; рекомендации сохраняют текущие действия скрытия/возврата.
- Доступные инструменты Pitchy с действием в контексте **собственного** проекта. Лимит показывать у конкретного инструмента, без четырёх больших карточек «Не назначено этому потоку».
- Для участника без проекта: «Мой профиль», доступные данные анкеты и команды, понятный разрешённый путь создать или привязать проект. Не подставлять фиктивный ID и не обещать создание там, где у пользователя нет прав.

### Паспорт

1. Развести два действия: работа с паспортом внутри кабинета и «Печать / сохранить PDF». Страница `/passport/[id]` может остаться экспортным представлением; основной кнопкой проекта она быть не должна.
2. Для владельца использовать существующий редактор и API с автосохранением/явным сохранением по текущему контракту. Показать отсутствующие обязательные поля и ожидаемое изменение заполненности.
3. Для активного члена команды определить серверный `can_view_passport`; по умолчанию — просмотр без редактирования. Право `can_edit_passport` выдавать только по явно утверждённой роли/правилу. Проверить принадлежность к активной команде и нужному потоку, а не доверять переданному `project_id`.
4. Для пользователя без доступа показывать объяснение и безопасный возврат в кабинет. Запретить чтение и изменение чужого паспорта прямым запросом.
5. Процент паспорта трактовать как расчёт заполненности по текущим правилам `passport.py`, а не как качество проекта или балл Demo Day.

## 2. Команда и поддержка

### Целевой экран

- Первый экран: назначенный трекер либо честное «Трекер пока не назначен», ближайшие и просроченные задачи, последняя обратная связь, статус недельного отчёта.
- «Заполнить отчёт» открывает форму по действию. Поля: состояние, что сделано, **«Что мешает»**, следующие шаги, какая помощь нужна. После отправки показать дату и историю; не создавать повторный отчёт случайным двойным нажатием.
- Задача и отзыв открываются по собственному ID из «Сегодня», уведомления и истории. После обновления страницы выбранный объект остаётся доступным.
- Командные действия вынести в отдельную вкладку/область с сохранением `TeamWorkspace`: приглашения, заявки, состав, роли, капитан, согласие на контакты, привязка проекта и выход.
- Область «Эксперты» добавлять только после проверки участнику разрешённых данных и действий. Текущий `MatchmakingWorkspace` скрывает экспертные связки при `membershipId`; это отдельная доработка, а не готовая вкладка.
- Контакт с трекером или организатором показывать только через реально работающий канал. Если его нет, не рисовать кнопку «Написать» без доставки.

### Серверные условия

- Для обзора поддержки нужен согласованный контракт с назначенным трекером, задачами, отзывами и отчётом; можно переиспользовать действующие данные `tracking` и `today`, не создавая вторую независимую историю.
- Прямые ссылки на задачу/отзыв должны проверять принадлежность текущему участию. Права капитана и согласие на публикацию контактов остаются серверными.
- При выключенном `progress_tracking` не показывать отчёты и задачи; при выключенном `matchmaking` не показывать командные действия. Не превращать отключение модуля в ошибку страницы.

## 3. Результаты

### Целевой экран

- Своё участие в Demo Day: собственная презентация, видео и материалы; состояние до отбора, ожидание оценки, финализация.
- После финализации три отдельные подписи: **«Оценка Demo Day — 80/100»**, **«Место — 1»**, **«Итог участия — участник»**. Оценка — среднее нормализованных экспертных баллов с поправкой организатора, ограниченное шкалой 0–100. Место рассчитывается по `final_score`. Итог участия устанавливается отдельно организатором; первое место автоматически не означает статус победителя.
- «Паспорт заполнен на 14%» показывать в контексте проекта, не рядом с итоговым баллом как часть рейтинга.
- Формулировку «Место X из N» использовать только после появления серверного общего количества. Нынешний API участника возвращает только собственный проект.
- Индивидуальные баллы, комментарии и рекомендации экспертов показывать только после явной политики публикации и изменения серверного ответа для **своего** проекта. Сейчас `evaluations` у резидента пуст даже после финализации. До этого — общий итог без обещания отзывов.
- Чужой рейтинг считать отдельной функцией: требуется настройка публикации потока, безопасный API и проверка видимости. В первую версию не включать.
- Сохранить собственные артефакты и настройки их видимости, существующий итоговый снимок и сценарий выпускника. Итоги должны оставаться доступны после `completed` по отдельному правилу доступа; `suspended` и `withdrawn` проверяются отдельно.

## 4. Навигация и техническая организация

1. Разделить крупный `ResidentWorkspace` по сценариям проекта, поддержки и результатов, сохранив текущие внешние контракты.
2. Хранить в URL допустимый раздел, контекст участия и выбранный объект. Переход из «Сегодня» или уведомления должен открыть нужный объект; обновление, кнопки браузера и мобильное меню не должны терять его.
3. Для асинхронного сохранения и загрузки защититься от смены проекта/участия, устаревшего ответа и повторной отправки.
4. Состояния `accepted`, `enrolled`, `suspended`, `completed`, `withdrawn` показывать понятными словами и только с разрешёнными действиями. Завершённый этап не объявлять выпуском без решения о завершении участия.
5. Сохранить доступность с клавиатуры, фокус после открытия детали, Escape и возврат, текстовые подписи статусов помимо цвета.

## Порядок реализации

### Этап 0. Контракты и права

- Зафиксировать матрицу доступа к паспорту: владелец, капитан, активный член команды, участник без проекта, посторонний, завершивший участие.
- Утвердить политику публикации личных экспертных отзывов и правило доступа к результатам после завершения.
- Определить capability-поля и защищённые методы для командного просмотра паспорта и личных отзывов. Решение об общем рейтинге оставить отдельным.

### Этап 1. Мой проект и паспорт

- Сделать обзор проекта и состояние «Мой профиль» без проекта.
- Подключить рабочее открытие паспорта в кабинете с разрешениями; экспорт оставить отдельным действием.
- Собрать аудит, рекомендации, инструменты и локальные лимиты без потери существующих функций.

### Этап 2. Команда и поддержка

- Собрать обзор трекера, задач и последней обратной связи.
- Свернуть недельный отчёт за кнопку и сохранить его историю.
- Встроить существующую команду и завершить переходы по ID задачи/отзыва.

### Этап 3. Результаты

- Исправить подписи балла, места, решения и заполненности паспорта.
- Добавить собственные опубликованные отзывы только после серверного контракта.
- Связать Demo Day, артефакты и итог участия; обеспечить разрешённое чтение после `completed`.

### Этап 4. Сквозная проверка

- Проверить прямые ссылки, обновление страницы, смену участия, пустые данные, ошибки и выключенные модули.
- Провести серверные тесты прав: владелец/член команды/посторонний, до и после публикации результатов, все жизненные статусы. Существующий тест `test_demo_day_selection_scoring_ranking_and_exports` фиксирует, что резиденту сейчас возвращаются пустые `evaluations`; при изменении политики этот контракт нужно обновить осознанно.
- Провести браузерные сценарии проекта, паспорта, команды, отчёта, задач, Demo Day и завершённого участия. Проверить ширины 360, 390, 768, 1280 и 1536 px; клавиатуру, фокус, контраст, отсутствие горизонтальной прокрутки и сравнение со скриншотами концепции.
- Выполнить TypeScript, линтер, подходящие серверные тесты и сборку; после публикации в `dev` проверить результат развёртывания.

## Критерии готовности

- Участник понимает, что сделать с проектом дальше, и открывает редактируемый либо доступный только для чтения паспорт в стиле кабинета. PDF обозначен как отдельный экспорт.
- Ни член команды, ни посторонний не могут изменить проект без подтверждённого сервером права.
- Поддержка показывает реального трекера, реальные задачи и отзывы; отчёт не занимает первый экран; все действия и ссылки ведут к нужной записи.
- Состав команды, приглашения, заявки, роли и согласие на контакты работают как до переработки.
- Число `80` однозначно подписано как балл из 100; место, решение организатора и заполненность паспорта не смешаны.
- Участник видит только опубликованные ему данные и только собственные результаты; разрешённая история доступна после завершения участия.
- Прямые ссылки, мобильная версия, пустые состояния и проверки прав покрыты браузерными и серверными тестами.
